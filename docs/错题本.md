## 2026-09-23 · grade-calculator：T2 编解码实现先于测试

| 项 | 内容 |
|---|---|
| **类型** | 规范违规（TDD 铁律：没有失败的测试就不写实现代码） |
| **现象** | s11 执行 T1 时顺手把 T2 的 `encodeState` / `decodeState` 一并实现了，T2 测试是后补的，没有经历 RED 阶段 |
| **根因** | 任务边界松懈——「同一模块里的相关函数」被当成了同一批实现对象，没有严格按任务规划逐个任务走 RED → GREEN |
| **正确做法** | 每个任务的函数范围在写实现前先划清；只有当前任务测试已经 RED 且验证过失败原因后，才写对应实现 |
| **规范修订** | 无需修订（DESIGN.md §10.5 已写明，属于执行违规而非规范缺口） |

## 2026-09-23 · grade-calculator：TS strictest 下守卫窄化不进闭包

| 项 | 内容 |
|---|---|
| **类型** | 类型错误（两次 typecheck 往返） |
| **现象** | `if (!(x instanceof HTMLInputElement)) throw` 守卫之后，嵌套的 `render()` 里引用 `x` 仍报 ts(18047) possibly-null，整片连坐 |
| **根因** | TS strictest 下控制流窄化不跨函数边界（闭包捕获的是声明类型）；第一版还用了一个独立的 `missing` 布尔做守卫，完全没有对变量本身窄化。另 `noUncheckedIndexedAccess` 使 `values[0]` 为 `number \| undefined` |
| **正确做法** | 守卫后立即创建对象别名（`const field = { input: x }`），嵌套函数只引用属性，不引用裸 querySelector 返回值；不用数组下标传值，逐个命名变量让 Result 窄化生效 |
| **规范修订** | 无需修订；结构与经验记入本工具页面注释，后续工具页照抄 |

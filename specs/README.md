## 3. 工作流（照这个走，不要自创）

### 3.1 骨架阶段（只做一次，已在进行中）

```
s3 技术栈 → s4 项目结构 → s5 开发规范（产出 DESIGN.md）→ s7 初始化
```

### 3.2 每个工具的三步（重复 5 次）

```
s8 需求澄清（产出 AC） → s11 TDD 实现（RED → GREEN → REFACTOR） → agent-browser 浏览器验收
```

**三步一步都不能省：**

| 步骤 | 为什么不能省 |
|---|---|
| s8 需求澄清 | 产出的验收标准（AC）是**唯一的验收依据**，必须写清边界情况 |
| s11 TDD 实现 | 铁律：没有失败的测试，就不写实现代码 |
| agent-browser 验收 | **测试通过 ≠ 功能对。** 必须真的打开页面、真的输入、截图给用户看 |

### 3.3 对话划分

- **一个工具 = 一个对话**（不要把所有工具塞进一个对话）
- 原因：每个工具的调试细节会挤占上下文，到第 5 个工具时模型对当前工具的专注度和 TDD 纪律都会退化
- **代价**：跨对话的一致性 100% 靠 `DESIGN.md` 承载，不靠对话记忆。所以 **DESIGN.md 必须写死到能照抄的程度**

### 3.4 其他场景

| 场景 | 用哪个 |
|---|---|
| 修 bug（代码行为与文档/AC 不符） | `s13-bugfix-workflow` |
| 需求变更（想加东西、改行为、改文案） | `s12-feature-evolution` |
| 发布（README / LICENSE / CONTRIBUTING） | `gh CLI` + `opensource-doc-generator` |

### 3.5 不要用的流程

**s1 需求澄清 / s2 产品概述 / s6 路线图**——这三步已经做完了，结论已固化在 `产品概述.md` 和根目录 `PROJECT-BRIEF.md` 里。**不要重做。**

## 5. 命名与位置规则

1. **工具的 slug 四处必须完全一致**：URL 路径 = `src/pages/tools/<slug>/` 目录名 = `src/lib/<slug>/` 目录名 = `specs/features/<slug>.md` 文件名。这是唯一能靠命名兜住的约束，别让它漂。
2. **工具编号是产品身份，开发顺序是排期**。产品上「工具 3」永远是化学工具；开发顺序是 1 → 2 → 4 → 5 → 3。
3. **一个工具的所有文档都叫同一个 slug**。例如成绩计算器若取 slug `grade-calculator`，则：`specs/features/grade-calculator.md`、`src/lib/grade-calculator/`、`src/pages/tools/grade-calculator/`。

## 6. 已知流程冲突（**需要用户手动修复**）

以下是 skill 文件与项目约定之间的矛盾。**Agent 无法自行修改这些 skill**（它们不是 agent 创建的），所以记录下来，遇到时按「处理方式」列执行，并提醒用户修。

| # | 冲突 | 影响 | 处理方式 |
|---|---|---|---|
| 1 | s11 的前置条件要求 `features/{名}.md` **+ `_技术方案.md` + `_任务规划.md` 三份齐全，缺一就拒绝开工**；但项目约定说「跳过 s9 / s10」 | **s8 → s11 直连会被 s11 拒绝** | **保留 s9 和 s10，但按最小篇幅做**（技术方案只写纯函数清单 + 输入输出 + 边界表；任务规划只写 3–6 个任务）。见下方 §6.1 |
| 2 | s11 与 s13 要求用 **Playwright MCP** 做浏览器验收 | 与项目约定的 `agent-browser` 职责重叠 | **以项目约定为准，用 `agent-browser`**。不要因为 skill 提 Playwright 就去装 Playwright |
| 3 | s5 里写的是 `spec/`（少一个 s），且文件名与 s3 / s4 的产出一致性不符（`spec/技术栈选型.md` vs 实际 `specs/技术栈.md`；`spec/项目目录结构.md` vs 实际 `specs/项目结构.md`），输出名也写成 `spec/开发规范.md` 而项目约定叫 `DESIGN.md` | 跑 s5 时容易找不到输入、或把输出写到错位置 | 跑 s5 时**显式告诉它输入是 `specs/技术栈.md` + `specs/产品概述.md` + `specs/项目结构.md`，输出到 `specs/DESIGN.md`**；并请用户修 skill |
| 4 | s5 要求读 `spec/API设计规范.md` 和 `spec/数据模型设计.md` | 本项目**无后端、无数据库**，这两个文件永远不存在 | 明确告知 s5 这两个章节写「当前阶段不适用，原因：本项目无后端、无数据库」 |
| 5 | s5 的 §5 是「框架特定规范（React / Vue / Svelte）」 | 本项目用 **Astro** | 按 Astro 写，不要生搬 React 规范 |

### 6.1 关于 §6.1 的说明：为什么不「跳过 s9 / s10」

项目约定原本写「单个工具太小，走 s9 / s10 是浪费，直接 s8 → s11」。但 s11 的执行前提是**它拿到一份已经拆好的任务清单**——没有任务清单，s11 不知道该按什么顺序写哪些测试。

所以真正浪费的不是这两步，是**为一个小工具写几十页的完整技术方案**。正确修法是「轻量化」而不是「跳过」：

- **s9 输出**：纯函数清单（每个函数的签名 + 输入输出含义）+ 边界情况处理表。**目标 1 页以内。**
- **s10 输出**：3–6 个任务，每个任务带验证标准（具体输入 → 预期输出）。**目标 1 页以内。**

## 7. 一条给所有 Agent 的提醒

用户不写代码。**任何方案、任何交付，都必须让用户能在不读代码的情况下判断它对不对。**

具体做法：每个工具交付时，同时给出「我该输入什么、预期看到什么」的验收清单，并用 `agent-browser` 真的打开页面截图。

如果某个方案用户无法判断对错，主动说明，并给出替代方案。
